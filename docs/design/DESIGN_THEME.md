# Theme Engine Architecture

`rio-theme` turns a client's *raw* brand color into the color the UI
actually uses. The two are not the same: the engine measures, repairs,
derives, and adapts the input before any of it reaches a stylesheet.

This document is the contract for that transformation — what each stage
does, the order it runs in, the thresholds it enforces, and the token
vocabulary it emits.

Pull request review runs against this document, not only the diff.

> **Doctrine inheritance**
> "No build step" and "`admin.css` is the single source of truth for
> design tokens" (ROADMAP notes 2 & 4) bound this engine: it runs at
> *build/CLI time*, emits a static `tokens.css`, and the runtime library
> **never links `rio-theme`** — it serves the generated bytes. See §1.3
> and §12.

---

## 1. Purpose

### 1.1 What this governs

- The pipeline `resolve_theme(ThemeInput) -> ThemeTokens` (`engine.rs`):
  a pure function, no I/O, no globals, same input → same output.
- The seven decision **Cases** that repair unsafe input (§7).
- The contrast thresholds every Case measures against (§3).
- The canonical `--rio-brand-*` token vocabulary and the drop-in
  `--rio-*` aliases the live admin consumes (§11).
- How a generated palette reaches a *running* admin (§12).

### 1.2 What this does not cover

- The runtime 6-token override patch — that is `AdminTheme` /
  `Admin::theme(...)`, an inline `<style>` block, not the engine.
- CSS layout, components, the cascade order of the baked bundle →
  `CLAUDE.md` "Templates and CSS" and `DESIGN_DOCTRINE.md`.
- The framework's own dark theme — the runtime ships **light and dark**,
  token-driven (`VISUAL-CONTRACT.md` §12). This doc covers how the *engine*
  emits a dark-aware `tokens.css` (§8 + `TOKENS-EMIT-SPEC.md`).

### 1.3 Closing principle

The engine is build-time only. A client's color is input; a safe,
contrast-checked `tokens.css` is output; the running framework only ever
handles the output's **bytes**. Any change that makes the `rustio-admin`
runtime crate depend on `rio-theme` is a doctrine violation — route it
through a generated file instead.

## 2. Color model & dependency footprint

- Colors are stored in **OKLCH** (`color.rs`): perceptually-uniform `l`
  (0..1), `c` chroma (0..~0.4), `h` hue degrees. sRGB hex is an **I/O
  concern only** — `from_hex` is the inbound door, `to_hex` the outbound.
  All engine math (`mix`, `lighten`, `darken`, hue distance, chroma
  checks) happens in OKLab/OKLCH and never round-trips through
  gamma-encoded sRGB mid-pipeline.
- The OKLab matrices are Björn Ottosson's published constants, embedded
  **literally** rather than computed at runtime, so `color.rs` stays
  self-contained and `cargo expand`-friendly.
- `from_hex` returns `ColorError` (never panics) — the engine accepts
  client-supplied strings.
- **The crate's only dependency is `log`** (warnings from the Case 1 /
  accent guards). WCAG luminance, OKLab conversion, and hex I/O are all
  hand-rolled, on purpose: the dependency footprint stays visible and
  auditable. Do not add a color crate to "simplify" this.

## 3. Contrast primitives

`contrast.rs` implements WCAG 2.1 once, correctly; Cases 1, 4, and 5 all
measure against it.

- `relative_luminance` works on linearized sRGB (`color::linear_srgb_of`
  owns the gamma curve — this file does not duplicate it).
- `contrast_ratio(a, b)` ranges `1.0..=21.0` (identical → 1.0,
  black-on-white → 21.0) and is symmetric.

| Constant | Value | Role |
|---|---|---|
| `AA_TEXT` | 4.5 | normal text |
| `AA_LARGE_TEXT` | 3.0 | large text (≥18pt / 14pt bold) |
| `AA_NON_TEXT` | 3.0 | UI components, icons, borders |
| `LIGHT_BG` | `#ffffff` | light-mode measurement background |
| `DARK_BG` | `#15161a` | dark-mode background (§8) |
| `TEXT_ON_LIGHT` | `#1a1a1a` | default near-black text |
| `TEXT_ON_DARK` | `#f5f5f5` | default near-white text |

---

## 4. The text guard — Case 1 (`guard.rs`)

The client's requested text color is a **suggestion**. `resolve_text_token`
returns it when it clears `AA_TEXT` on the surface; otherwise it logs a
warning and substitutes `readable_text` (whichever of `TEXT_ON_LIGHT` /
`TEXT_ON_DARK` reads better). The rejected color is **never destroyed** —
callers may still place it on a border or divider.

This is the engine's central guarantee: every text-on-surface pairing it
emits clears AA. `engine.rs` runs the final guard pass over `brand_text`
on `bg` and a `debug_assert!` re-checks the emitted pair so a future
`ThemeTokens` field can't slip an unmeasured pairing past the guard.

---

## 5. Derivation — Case 2 (`derive.rs`)

`derive_palette(brand)` expands one brand color into the functional
shades. The canonical wording is **"brand mixed N% into white/black"**;
with `a.mix(b, x)` = `(1−x)·a + x·b`, "10% brand into white" is
`brand.mix(white, 0.90)`:

| Token | Mix |
|---|---|
| `brand_tint` | 10% brand into white (`mix(white, 0.90)`) — light fills |
| `brand_hover` | 88% brand + 12% black — hover on solid buttons |
| `brand_active` | 75% brand + 25% black — active/pressed |
| `brand_text` | 72% brand + 28% black — *then re-checked by Case 1* |
| `bg` | 3% brand into white — page canvas |
| `border` | 14% brand into white — hairline |
| `muted` | 35% brand into `#6b7280` (gray-500) — brand-temperatured neutral |

Semantic state colors are **not** derived here — they are universal
conventions owned by Case 4.

## 6. Role-fit scoring (`hierarchy::surface_fitness`)

`surface_fitness(color)` scores how well a color carries large surfaces:

```
contrast_score  =  ln(contrast_ratio(white, color)).max(0)   // log-shaped: 7.0 doesn't dwarf 4.5
lightness_penalty = (l − 0.55)²                               // distance from a comfortable mid-tone
chroma_penalty    = ((c − 0.10).max(0))² · 4                 // vivid colors tire the eye at scale
fitness = contrast_score − lightness_penalty − chroma_penalty
```

It rewards readable contrast and penalises both excessive chroma and
extreme lightness. Used by §9 (ranking) and conceptually by §7 Case 3.

## 7. The seven Cases

Each Case is one repair the engine may apply. The CLI report
(`rustio-admin theme generate`) names them so the operator sees exactly
what fired.

- **Case 1 — text contrast guard** (`guard.rs`, §4). Substitute a
  readable text color when the requested one fails AA.
- **Case 2 — palette derivation** (`derive.rs`, §5). One brand → tint /
  hover / active / text / bg / border / muted.
- **Case 3 — vivid taming & role split** (`vivid.rs`). Above
  `VIVID_CHROMA_THRESHOLD` (0.16 OKLCH) a brand splits into two siblings:
  the raw color for **small touches** (`accent`) and a tamed sibling for
  **large fills** (`surface`). The tamed surface targets chroma
  `threshold·0.75` and clamps lightness into `[0.35, 0.65]` so it can
  carry either text color. **Hue never moves** — a tamed lime still reads
  as lime. Calm brands (teal ~0.13) pass through untamed.
- **Case 4 — brand-vs-state collision** (`semantic.rs`). Success/warning/
  danger are fixed anchors (`#16a34a` / `#d97706` / `#dc2626`), *not*
  brand-derived. The only adjustment is rotating a state out of the
  brand's hue when they collide (target gap `MIN_HUE_GAP` 45°), **capped
  at `MAX_STATE_ROTATION` 30°** so a state never leaves its conventional
  band (red→amber, green→teal are forbidden — a wrong-colored state is
  worse than a small gap). An achromatic brand (`chroma < ACHROMATIC_CHROMA`
  0.02) short-circuits: hue is undefined, states stay unshifted.
- **Case 5 — mode-adaptive brand** (`adaptive.rs`). A brand faces both
  `LIGHT_BG` and `DARK_BG`; the engine measures each independently and
  edits **only the failing mode**, stepping lightness ±0.05 for up to 20
  iterations until it clears `AA_NON_TEXT`. `*_adjusted` records "we
  tried"; `*_clears_aa` records "we succeeded" — they are distinct so a
  failing token is never silently trusted.
- **Case 6 — multi-color role assignment** (`hierarchy.rs`, §9). N colors
  → one primary, one secondary, the rest chart series. No color dropped.
- **Case 7 — default brand fallback** (`engine.rs`). No input →
  `DEFAULT_BRAND` `#3f6089`, a quiet blue-gray that passes contrast on
  white and sits mid-lightness so it survives a future dark mode.

## 8. Dark-mode structure

The framework ships a real dark theme, so a generated `tokens.css` **must** be
dark-aware. `emit.rs` writes the framework's full dual dark structure — an
explicit `:root[data-theme="dark"]` block **and** a
`@media (prefers-color-scheme: dark) { :root { … } }` auto block — with identical
values, via a [`DarkPolicy`] (auto-derive / light-only / explicit). A `:root`-only
override would tie `[data-theme="dark"]` on specificity and win by source order,
leaking light into dark; the dual structure prevents that. The full contract for
generators (in-repo and the external `rustio-design`) is
[`TOKENS-EMIT-SPEC.md`](TOKENS-EMIT-SPEC.md); the framework also logs a startup
WARN if a `RUSTIO_TOKENS_CSS` override is light-only.

## 9. Brand ranking — fitness, not input order

`assign_roles` (Case 6) **stable-sorts the inputs by `surface_fitness`
descending**: `primary = ranked[0]`, `secondary = ranked[1]`, `chart =
ranked[2..]`. The client's stated order is a **tiebreaker, not the sole
signal** — a client's first color is sometimes too vivid for the primary
role, and ranking by fitness keeps the UI readable. The stable sort
preserves input order on equal fitness.

Edge cases use a sentinel: zero or one input returns `secondary == primary`,
which `engine.rs` reads as "no real second color" and substitutes its own
post-tame hover (avoids deriving a secondary from a raw, possibly-vivid
input).

## 10. Pipeline stage order

Order matters; each stage consumes the previous stage's output
(`resolve_theme_with_report`):

1. **Case 7** — empty input → `DEFAULT_BRAND`.
2. **Case 6** — `assign_roles` → primary / secondary / chart.
3. **Case 3** — `split_vivid_roles(primary)` → raw `accent` + tamed `surface`.
4. **Case 5** — `adaptive_brand(surface)` → light / dark variants.
5. **Case 2** — `derive_palette(surface)`. **Derive runs on the *tamed
   surface*, not the mode-adapted variant** — otherwise hover/active
   would drift differently in light vs dark mode.
6. **Case 4** — `resolve_semantics(primary)` → success / warning / danger.
7. **Case 1** — final guard pass: `resolve_text_token(bg, brand_text)`,
   plus a non-text guard on `brand_accent` (if the raw accent fails
   `AA_NON_TEXT` on `bg` it is substituted by the tamed surface — same
   hue family, known-safe). Then all contrast measurements are recorded
   into `ResolveReport` post-resolution so the CLI numbers match the
   emitted tokens.

`brand_secondary`: a real second color when the input supplied one,
otherwise the derived hover (the §9 sentinel).

## 11. Token vocabulary (`emit.rs`)

The output is **plain hex** — all `color-mix()` math is pre-computed by
the engine, so the static file parses fast with zero browser-support
risk. One `:root` block carries two sections:

**Canonical `--rio-brand-*` (engine output):** `-light`, `-dark`,
`-adaptive` (`var(--rio-brand-light)`, flipped to `-dark` under
`[data-theme="dark"]`), `-surface`, `-accent`, `-secondary`, `-hover`,
`-active`, `-tint`, `-text`, plus `--rio-muted`.

**Drop-in aliases for the live admin** — these make the file an actual
drop-in for the framework's `colors.css`:

- `--rio-accent` tracks **`brand_surface`** (the tamed "large fills"
  role), *not* the raw `brand_accent` — buttons must stay readable for
  neon inputs. `--rio-accent-hover`, `--rio-accent-soft` (= tint),
  `--rio-accent-rgb` (space-separated triple, quantized to agree with
  the accent hex), `--rio-accent-border` (= `brand_surface` lightened
  0.65). `--rio-bg`.
- **Slate scaffold** (`--rio-surface*`, `--rio-text*`, `--rio-border-soft`,
  `--rio-border-strong`) is **brand-agnostic** — copied from the live
  `colors.css` so a brand swap doesn't move the chrome ladder out from
  under existing components. `--rio-border` is brand-derived.
- **Semantic** foregrounds + matching soft backgrounds. `soft_bg` walks
  from 92% white toward lighter in 1% steps until the foreground clears
  `AA_NON_TEXT` against it (bounded at 99%) — a flat 92% mix leaves amber
  warning at 2.94, below the 3.0 floor.
- `--rio-chart-N` (1-indexed) for each chart-series color.

> **Lock-step rule:** the alias list and the live `colors.css` must not
> drift, or the generated file stops being a drop-in. The
> `emit_contains_every_live_template_token` test guards this — update both
> together.

## 12. Consumer integration

Two distinct loops apply engine output to a UI:

1. **Framework default (build-time).** `assets/static/admin/tokens/colors.css`
   is itself `/* Generated by rio-theme */` (the `DEFAULT_BRAND` palette),
   committed and baked into the `ADMIN_CSS` `concat!` bundle. Regenerate it
   with `theme generate` and commit the result; never hand-edit it.

2. **Project palette (runtime).** A project runs:

   ```sh
   rustio-admin theme generate --brand '#2563eb' --out tokens.css
   RUSTIO_TOKENS_CSS=./tokens.css cargo run
   ```

   `/static/admin.css` appends the file's bytes **after** the baked
   bundle (`admin_css_payload` in `admin/routes.rs`), so its `:root`
   block wins the cascade — later `:root` wins, no `!important`, exactly
   like the `AdminTheme` inline patch. The file is read once at
   router-build time (the route is `no-cache`, so a restart rolls out an
   edit); a set-but-unreadable `RUSTIO_TOKENS_CSS` logs a warning and
   degrades to the baked bundle rather than failing boot.

The runtime serves bytes only — neither loop links `rio-theme` into the
`rustio-admin` runtime crate (§1.3).
