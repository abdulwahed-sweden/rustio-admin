# REVIEW_BUILDER_DOCTRINE.md — Critical review of DESIGN_BUILDER.md

This document is a defensive review of [`DESIGN_BUILDER.md`](../design/DESIGN_BUILDER.md).
It is written from the perspective of a reviewer who must defend the
Builder's adoption inside regulated enterprise environments (bank,
hospital, factory, payment processor), where a single doctrine gap
becomes a compliance audit finding.

The review is critical, not supportive. It is grounded in
cross-references against the existing framework doctrines
(`DESIGN_AUDIT.md`, `DESIGN_SESSIONS.md`, `DESIGN_RECOVERY.md`,
`DESIGN_R2_ORGANISATIONAL.md`, `DESIGN_R3_MFA.md`,
`DESIGN_R4_EMERGENCY.md`).

**Revision history.**

- Original review against the first-draft doctrine surfaced six
  **B**locker, seven **S**ignificant, and four **M**inor findings.
- A revised `DESIGN_BUILDER.md` closes every blocker and the
  user-prioritised significant findings. This document tracks the
  resolution of each finding.

---

## 0. Methodology

Each finding is anchored in:

1. A specific section or invariant in `DESIGN_BUILDER.md` (cited).
2. Either a contradicting doctrine in the existing framework
   documents (cited), an undefined property that an enterprise
   reviewer would refuse to sign off on, or a class of attack /
   failure that the current wording does not foreclose.

Findings are graded **B** (blocker — implementation cannot begin
honestly until resolved), **S** (significant — must close before v1.0
freeze of the Builder), **M** (minor — clarification, no
architectural shift required). Each finding is also marked with its
current state:

- **RESOLVED** — fixed in the revised `DESIGN_BUILDER.md`.
- **PARTIAL** — substantially addressed but a residual gap remains.
- **OPEN** — not yet closed; tracked for a future doctrine revision.

## 1. Findings

### 1.1 Two parallel append-only logs without a reconciliation contract — **B** — **RESOLVED**

**Original concern.** `DESIGN_AUDIT.md` §1.1 and §5.6 establish
`rustio_admin_actions` as *the* append-only audit row family for the
project. `DESIGN_BUILDER.md` introduced a second append-only event
log (`.rustio/history.jsonl`) without declaring the relationship.

**Resolution.** §1.2 and §12 of the revised doctrine carve the
boundary explicitly. `history.jsonl` is a **build-time** intent log;
`rustio_admin_actions` is a **runtime** authority-mutation log. They
do not federate. The revised doctrine inherits Doctrines 8 / 11 / 18
from `DESIGN_AUDIT.md` by analogy (Doctrines B2 / B3 / B4) rather
than merging the two logs. The `HistoryOp` enum is the typed-event
source of truth on the Builder side, symmetric to `AuditEvent` on
the runtime side, with its own drift test (§10.8).

### 1.2 No redaction discipline for `history.jsonl` — **B** — **RESOLVED**

**Original concern.** `DESIGN_AUDIT.md` Doctrine 11 (`audit::redact`
produces fingerprints, not values) was unrepresented in the Builder
doctrine. Default values for secret-class fields, env vars, and
SMTP credentials could land in `history.jsonl` plaintext.

**Resolution.** §4.2.3 declares a closed list of redaction
categories. The redactor `cli::redact` is the sole boundary, enforced
by grep proof (§10.5). A property test asserts no 4-char input
substring leaks, symmetric to `DESIGN_AUDIT.md` §5.3. Doctrine B4
binds the discipline at the invariant level. The CLI's `@redact:`
sigil at the input boundary gives the developer an explicit
plaintext-protection escape valve.

### 1.3 Reproducibility is asserted but not bounded — **B** — **RESOLVED**

**Original concern.** The byte-for-byte replay claim was
unenforceable as written. TOML has no canonical serialization;
locale, line endings, Rust toolchain version, and the Builder's own
version all silently affected output.

**Resolution.** §4.4 declares the closed set of environment fixings
(locale `LC_ALL=C`, LF line endings, UTF-8 NFC, the canonical TOML
emitter `cli::toml::emit_canonical`, second-precision ISO-8601
timestamps, ULID-on-write semantics, pinned Builder version,
project-pinned rustc). The reproducibility property is now stated
*under these fixings* and is unspecified outside them. Three
enforcement primitives back it: the canonical-emitter grep proof
(§10.4), the round-trip drift test, and the replay drift test
against a fixture corpus.

### 1.4 The Builder version is a hidden second runtime — **B** — **RESOLVED**

**Original concern.** The `// @generated by rustio <version>` header
embedded build-time metadata into compiled artefacts, and the
doctrine did not forbid the Framework from reading it. Version drift
between developer Builders was silently permitted.

**Resolution.** Two doctrines now bind:

- Doctrine B10 forbids the Framework crate from reading
  Builder-emitted metadata at runtime. The grep proof in §10.2
  rejects any match for `@generated by rustio`, `SPDX-SchemaHash`,
  or `SPDX-EmitterVersion` under `crates/rustio-admin/src/`.
- Doctrine B11 introduces `.rustio/builder.lock` (§4.3). Every
  command except `rustio upgrade` refuses to run on a version
  mismatch. The header text is explicitly excluded from the
  SchemaHash projection (§5.3) so visible version bumps do not
  trigger spurious regeneration.

### 1.5 `features` table can disable audit-by-default — **B** — **RESOLVED**

**Original concern.** `[features] audit = false` was implicitly
permitted, contradicting `DESIGN_AUDIT.md` Doctrine 8.

**Resolution.** §8.1 and §8.2 split the feature space into two
disjoint closed lists. The doctrine-bound list (§8.2) enumerates
`authentication`, `audit`, `csrf_protection`, `correlation_id`,
`redaction`, `single_writer_invalidation`. Doctrine B7 binds the
refusal: any `false` value for a doctrine-bound member fails
`rustio commit` with a doctrine-violation error. The
`cli::config::tests::doctrine_bound_features_rejected` drift test
and the §10.3 grep proof together prevent silent introduction of a
new bypass route.

### 1.6 Single-writer rule for `history.jsonl` is absent — **B** — **RESOLVED**

**Original concern.** `DESIGN_SESSIONS.md` Doctrine 22 establishes
that a single named function writes `revoked_at`. The Builder log
had no equivalent — anyone in the CLI crate could append. No grep
proof was possible.

**Resolution.** Doctrine B3 names `cli::history::append` as the sole
writer. §10.1 specifies the grep proof: exactly one function
definition in `crates/rustio-admin-cli/src/history.rs`, and zero
write handles to `history.jsonl` constructed elsewhere. The
discipline is the explicit Builder analog of Doctrine 22 and is
called out as such in §12.

### 1.7 `--force` overwrite has no provenance trail — **S** — **RESOLVED**

**Original concern.** A `--force` overwrite of a hand-edited
generated file silently destroyed work, with no audit trail and no
dirty-git-tree refusal.

**Resolution.** §5.4 case 3 now requires:

- The prior file's bytes copied to `.rustio/forced/<timestamp>/<path>`
  before overwrite.
- A `forced_overwrite` event in `history.jsonl` carrying the prior
  SHA-256 and the actor.
- Refusal against a dirty git tree unless `--accept-dirty` is also
  supplied (independent flag; neither implies the other).
- `--accept-dirty` itself emits an event.

The same provenance discipline applies to `--force` deletion (§5.5).

### 1.8 Concurrent writers / git merge is undefined — **S** — **RESOLVED**

**Original concern.** Two engineers branching `.rustio/` produced
interleaved `history.jsonl` streams with possibly-conflicting state.
The doctrine did not address merge.

**Resolution.** §4.5 declares mergeability *iff the textual three-way
merge produces a line sequence that replays to a well-formed
`draft.toml`*. The `rustio merge` verb performs the verification,
emits a `merge_verified` event recording the merge parent SHAs on
success, and refuses on mismatch. Cross-branch conflicting renames
surface as merge failures requiring human resolution; the Builder
does not auto-resolve. The replay invariant (§4.2.2) is the
enforcement primitive.

### 1.9 No deletion contract for `_generated/` — **S** — **RESOLVED**

**Original concern.** §4.3 covered create and overwrite but not
deletion. A removed model's generated file disappearing was
unspecified.

**Resolution.** §5.5 specifies the deletion contract symmetric to
overwrite: SchemaHash check; emission of a `file_deleted` event with
the prior SHA-256; atomic inclusion in the parent `commit`
transaction; quarantine of prior content under `.rustio/forced/`
when `--force` is used.

### 1.10 Schema migration of `draft.toml` itself has no roll-back contract — **S** — **RESOLVED**

**Original concern.** `schema_version` migrations were described as
forward-only but with no snapshot, no event emission, and no
declared recovery path.

**Resolution.** §4.6 specifies:

- Pre-upgrade `draft.toml` snapshotted to
  `.rustio/draft.toml.v<old>.bak`.
- A `schema_upgraded` event in `history.jsonl` carrying from/to
  versions and a digest of the prior file.
- Forward-only formally declared; downgrade is manual restoration
  from `.bak`.
- Event-replay across upgrades is the explicit responsibility of
  `cli::history::replay`, with a drift test in §10.8 covering every
  supported `(from_schema, to_schema)` pair.

### 1.11 "Destructive operation" is enumerated too narrowly — **S** — **RESOLVED**

**Original concern.** The phrase "or any other data-loss operation"
left the classification to implementer judgement. Lossy casts,
late-arriving `NOT NULL`, `UNIQUE`, `CHECK`, constraint drops, and
renames without enabling events were unspecified.

**Resolution.** §7.3 declares a closed enumeration (D1–D10) with
explicit SQL patterns and notes. Future destructive classes are
added via doctrine amendment, not by judgement. "Or any other" is
removed from the doctrine.

### 1.12 No model rename without data loss — **S** — **RESOLVED**

**Original concern.** A `draft.toml` rename surfacing as
`DROP + CREATE` silently destroyed data. The doctrine did not declare
which input (`draft.toml` final state vs. `history.jsonl` intent)
governed the discrimination.

**Resolution.** Doctrine B12 binds the rule: rename is performed only
when a `rename_*` event exists. §7.4 spells out the discrimination
procedure. A hand-edit that drops and re-adds is unambiguously
treated as drop+create requiring `--accept-destructive`. The
doctrine "privileges event-recorded intent over final-state
similarity" is now an explicit design choice.

### 1.13 No air-gap declaration is binding on the Framework — **S** — **PARTIAL**

**Original concern.** The Builder's `no network in plan or commit`
rule was solely a Builder property; the Framework's own runtime
network discipline was unaddressed.

**Resolution.** §6.3 of the revised doctrine notes the scope: *"The
same rule does not bind the Framework runtime — that is the
Framework's own contract surface (`DESIGN_RECOVERY.md`,
`DESIGN_EMAIL.md` govern its runtime network discipline)."* This
prevents the half-answer the original review flagged, but it does
not introduce a Framework-level air-gap doctrine. That belongs in a
future Framework-doctrine amendment, not here.

**Residual gap.** Air-gap compliance of a generated *project* is the
union of two independent doctrines. The revised Builder doctrine
makes the boundary explicit; closing the union claim requires a
companion change in the Framework documents and is not Builder
scope.

### 1.14 Rollback hints in migrations open a precedent — **M** — **RESOLVED**

**Original concern.** SQL comments in migrations established a
contamination channel from Builder to Framework.

**Resolution.** §7.5 declares rollback hints **free-form
human-readable text**, not parseable. The Framework's migration
runner must not parse them; a future need for structured metadata
goes in a sidecar file. The contamination precedent is closed.

### 1.15 `main.rs` ownership is unstable — **M** — **RESOLVED**

**Original concern.** §4.1 of the original draft declared `main.rs`
developer-owned forever, but new-model registration must reach
`main.rs` somehow. The first feature would violate the rule.

**Resolution.** §5.1 of the revised doctrine declares the
single-function escape: `_generated/admin.rs` exposes
`build_admin() -> rustio_admin::Admin`, and `main.rs` calls into
it. New model additions update `build_admin`, not `main.rs`. The
boundary is preserved.

### 1.16 No "Builder doctor" coverage of `.rustio/` integrity — **M** — **OPEN**

**Original concern.** Two new files (`draft.toml`, `history.jsonl`)
with strong invariants had no doctrine-declared verification command.

**Status.** §10.8 enumerates the drift tests that any implementation
must include. §13 notes that `rustio doctor builder` is not yet
documented as a separate verb obligation. The drift tests are the
implementation-level enforcement; the operator-facing single-command
verification surface is acknowledged as a gap.

**Residual gap.** A future doctrine revision should declare the
verb-level obligation (verify `builder.lock`, replay `history.jsonl`,
recompute every SchemaHash, report drift). Until then, operators
must invoke the underlying CI drift tests by hand. The implementation
need is the same; only the developer-facing UX is missing.

### 1.17 Advisory layer can launder writes through accepted proposals — **M** — **RESOLVED**

**Original concern.** A future `rustio review --accept-all` flag
could shortcut human review and let Advisor content land in
`draft.toml` with no provenance trail.

**Resolution.** Doctrine B13 and §9.3 close the loop. Any Builder
command that writes Advisor-originated content to `draft.toml`
records the proposal ID, reviewer identifier, and verdict in
`history.jsonl`. Acceptance under `RUSTIO_AGENT_MODE=1` is permitted
but the verdict event uses an `actor` prefixed `agent:` so a grep
on the log distinguishes human-approved from agent-approved writes.
No flag suppresses the verdict event. The grep on the log answers
"who actually approved this change" months after the fact.

## 3. Doctrine consistency assessment — post-revision

The revised `DESIGN_BUILDER.md` now matches the framework's existing
doctrine quality bar. Specifically:

- **Doctrine inheritance** is declared at the document head with
  named mappings: B3 ↔ Doctrine 22, B4 ↔ Doctrine 11, B2 ↔
  Doctrines 8 / 18.
- **Single-writer enforcement** is grep-provable (§10.1) symmetric
  to the framework's existing Doctrine 22 grep proof.
- **Typed-event discipline** is enforced by the `HistoryOp` enum
  drift test (§10.8), symmetric to the `AuditEvent` drift test.
- **Redaction discipline** is grep-provable (§10.5) and
  property-tested (§10.8), symmetric to `audit::redact`.
- **Closed enumerations** replace prose hand-waves: destructive
  operations (§7.3 D1–D10), feature toggles (§8.1 / §8.2),
  redaction categories (§4.2.3).
- **Atomicity, idempotence, and reproducibility** are bounded
  (§4.4, §6.2, §6.4).
- **Threat model** is formal (§3), enumerating adversaries and
  their defeating properties — the same structure as
  `DESIGN_AUDIT.md` §3 and `DESIGN_SESSIONS.md` §3.

A reviewer comparing the Framework doctrines to the Builder doctrine
will no longer conclude the Builder document is structurally weaker.
The enforcement primitives (grep proofs, drift tests, property
tests) are now named and CI-targeted.

## 4. What the next revision must add

In order of dependency:

1. **1.13 — Framework-side air-gap doctrine.** A Framework-doctrine
   amendment that declares the runtime network surface (recovery
   email, future MFA push notifications, etc.) as bounded under a
   named opt-out. Out of Builder scope; tracked here for cross-doc
   visibility.
2. **1.16 — `rustio doctor builder` verb-level obligation.** The
   underlying drift tests exist in §10.8; the operator-facing
   single-command verification needs to be promoted to doctrine.
3. **Exhaustive `draft.toml` schema.** A separate document
   versioned alongside `schema_version`, covering every permitted
   modifier, validation rule, and the registry of types
   (`text`, `decimal`, `id`, foreign-key syntax, …).
4. **`DESIGN_ADVICE.md`.** The Advisory AI's internal contract.
   This document binds only the boundary; the interior is
   undocumented.
5. **`DESIGN_STUDIO.md`.** Studio's surface specification.

Findings 1–13 above no longer block the next phase of work. The
Builder doctrine is implementation-grade.

---

## 5. Verdict

> **Implementation-grade.** All six blocker findings are resolved.
> Six of seven significant findings are resolved; the seventh
> (1.13) is partially resolved with a residual gap that belongs in
> Framework doctrine, not Builder doctrine. The doctrine matches
> the framework's quality bar for enforcement primitives (named
> single-writers, grep proofs, drift tests, property tests, closed
> enumerations) and is now adoptable as the design contract for a
> Builder MVP.

The verdict change from the original review: *Not implementable as
written* → **Implementation-grade**, with two documented residual
gaps (1.13 air-gap, 1.16 doctor verb) that do not block the
beginning of implementation but must close before the Builder's own
v1.0 API freeze.

The doctrine is now load-bearing. Future PRs to the Builder
implementation are reviewed against `DESIGN_BUILDER.md` first, this
review document second (for residual gaps), and the code diff third.
